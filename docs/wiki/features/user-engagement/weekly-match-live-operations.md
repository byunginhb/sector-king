# 주간 섹터 매치 — 운영 DB와 자동 실행

상태: 운영 DB 적용 · 단일 라운드 자동 실행 준비 · 사용자 공개 대기
기준일: 2026-11-09 UTC. 이 문서는 [초기 수동 운영 절차](weekly-match-operations.md)의 후속 운영 기준이다.

## 적용 범위

기존 Supabase `sector-king` (`jbatgxigzrxwthcmaran`)에 `0018_weekly_match.sql`을 적용했다. 공개 API는 빈 목록으로 정상 응답하며 운영 라운드·선택·정산은 아직 0건이다. 세 테이블에 RLS가 적용되고 사용자는 본인 선택만 읽는다. 선택 쓰기는 로그인 사용자의 신원을 사용하는 전용 RPC만 허용한다. 운영 원본 가격·감사 JSON은 공개 API에 노출하지 않는다.

자동 정산 보호 마이그레이션 `20261109014835_weekly_match_automatic_guard.sql`도 운영 DB에 적용했다(운영 이력 `20261109015512`). 이 함수는 같은 라운드 잠금 안에서 최신 결과를 다시 확인한다. 이미 확정된 승리·무승부·무효 결과는 자동 작업이 덮어쓰지 못한다. `pending`만 재확인하며 자동 무효는 종료 7일 이후에만 허용한다. 수동 정정은 기존처럼 명시적인 사유와 별도 운영 호출이 필요하다.

## 실행·복구·중지

[Weekly Match workflow](https://github.com/byunginhb/sector-king/actions/workflows/weekly-match.yml)는 `main`에서만 실행한다. 기존 GitHub `CRON_SECRET`, `CRON_TARGET_URL`을 Actions 안에서 재사용하며 값을 복사하거나 출력하지 않는다. 공개 GET과 잘못된 본문 `{}`에 대한 인증 후 HTTP 400 응답으로 서버 연결을 검사한다. 기준일 전에는 `waiting-base`, DB 쓰기 없이 종료한다.

첫 게시 전에 기준 가격과 출처를 `weekly-match-baseline-kr-2026-11-16` artifact에 저장한다. 게시 타임아웃 이후에도 같은 원본을 복원해 재전송한다. 현재 저장소·main·해당 workflow·실행 이벤트·커밋을 확인한 artifact만 복원한다. 이미 게시됐는데 원본이 없거나 설정이 바뀌었으면 중단하며 가격을 다시 만들어 덮어쓰지 않는다.

정산 원본도 전송 전에 별도 artifact로 보존한다. 조회 시간 초과·소켓 오류도 결측 증거로 기록한다. 각 종목의 결측·기업행사는 `pending`으로 남기고 비중을 재분배하지 않는다. 종료 7일이 지나도 미확인이면 무효 처리한다. 확정 결과는 다음 실행에서 건너뛴다. 한 실행은 최대 15분이며 코드 내 즉시 반복 재시도는 없고, 실패 상태와 Actions 요약을 확인한 뒤 원인을 수정한다. 다음 일일 실행은 다시 확인할 수 있다. 추가 이메일·Slack 발송은 설정하지 않았다.

중지: `gh workflow disable weekly-match.yml` 또는 GitHub Actions 화면에서 Disable workflow. 설정의 `enabled:false`도 모든 수집·전송을 중지한다. 이 설정은 웹 진입 노출 플래그와 별개다. 이번 라운드가 확정된 뒤 workflow를 중지하고 다음 라운드는 달력·구성 종목을 다시 검토한다. Artifact 보관은 90일이므로 장기 보존이 필요하면 만료 전에 운영 담당자가 내려받아 보관한다. 누락·만료 시 자동 복구는 중단한다.

수동 재실행: `gh workflow run weekly-match.yml --ref main`. 실제 실행 성공, 첫 게시, 첫 접수, 첫 정산을 각각 구분해 확인한다. 새 코드는 새 마이그레이션 적용 후 배포한다. 중지는 원장을 삭제하지 않으며 롤백 시에는 먼저 workflow를 중지하고 기존 데이터를 보존한다.

## 공개 전 남은 검증

`WEEKLY_MATCH_ENABLED`는 켜지 않았다. `/weekly-match`는 직접 접근할 수 있지만 검색 `noindex`와 sitemap 제외를 유지한다. 실제 OAuth 사용자로 본인 선택 저장·변경을 확인하고 기준 종가 수집과 최초 게시가 성공한 뒤 진입 링크 공개를 판단한다. 현재 브라우저 연결이 없어 실제 OAuth 검사는 수행하지 못했다.

운영 DB에서는 합성 사용자·라운드를 트랜잭션 안에 만들고 본인 선택 갱신, 타인 기록 차단, 직접 쓰기 거부, 마감 거부를 확인한 뒤 전부 롤백했다. 이 검사는 실제 PostgreSQL/RLS 검사이며 OAuth 로그인 성공을 뜻하지 않는다. 기존 사용자 데이터를 시험에 사용하지 않았다. 공개 anon 키의 실제 PostgREST 조회·쓰기 거부도 확인했다.

기존 Supabase 보안 advisor의 함수 search_path·기존 security-definer 권한·유출 비밀번호 검사 알림은 이번 작업 이전부터 존재한다. 운영 전용 두 테이블의 정책 없는 RLS는 클라이언트 접근을 차단하려는 설계다. 이번 작업에서 기존 인증 설정을 변경하지 않았다.
