# 주간 섹터 매치 — 운영 DB와 자동 실행

상태: 자동 운영 전환 · 첫 자동 대진의 실제 기준 종가 대기
기준일: 2026-11-26 한국시간. 이 문서는 [초기 수동 운영 절차](weekly-match-operations.md)의 후속 운영 기준이다. 주간 대진의 원본·마감·종료는 유지하며, 사용자가 승인한 조기 검증용 별도 대진·두 라운드 운영·베타 진입은 [11/18 단기 베타 운영](weekly-match-pilot-2026-11-18.md)을 따른다. 11/16 당시의 단일 runner·공개 대기 조건은 변경 전 이력이다.

## 자동 운영 전환 — 11/26

사용자가 주기적 생성·검수·게시·정산·기존 보상 연결을 승인했다. 현재 기준은 [자동 운영 절차](weekly-match-automatic-operations.md)다. 기존 수동 대진과 비활성 후보는 보존하며, 별도 자동 ID로11/30 주부터 계획한다. 미래 기준 종가가 준비되기 전에는 게시하지 않는다. 아래 수동 전환 조건과 단일/두 manifest 실행 설명은 자동 운영 도입 전 이력으로 보존한다.

## 최신 확인 — 11/26

첫 대진의 보존 원본과 별도 산식으로 공개 버전2 결과를 재현했다. 은행7·조선5의 기준·종료 24종가는 Npay의 명시적 정규장 종가 필드와 모두 일치했다. 기존 신한 가격 차이는 정규장 종가와 애프터마켓 포함 최종가의 차이로 확인됐다. 수집기에 동일한 대조를 추가했으며, 불일치·누락·원천 장애 시 게시를 중단하고 정산은 기존 보류 규칙을 따른다.

새 접수는 아직 없고 운영 원장은 변경하지 않았다. 다음 검토 대상은 11/27 기준·11/30 마감·12/4 종료이며, 실제 미래 종가와 게시 직전 확인이 남아 있다. 정확한 검증 범위·순서·한계는 [11/26 후속 절차](weekly-match-next-steps-2026-11-26.md)를 따른다. 아래 11/21 기록은 당시 확인 범위다.

## 최신 운영 확인 — 11/21

- 실제 공개 API는 `kr-2026-11-16`의 최신 버전2, 한국 은행 우세(`left`)를 반환한다. 은행 -3.212589%, 조선 -7.243264%로 두 섹터 모두 하락한 기간의 상대 비교다. 이 값은 운영 자동 집계 결과이며 독립 가격 원장 검증을 뜻하지 않는다.
- [11/21 예약 실행](https://github.com/byunginhb/sector-king/actions/runs/44926124370)은 success다. 보존된 weekly plan의 action은 settle, receipt는 version2/outcome left다. pilot plan은 disabled다.
- 해당 실행은 11/21 09:05 UTC 예약에 대해 실제16:43:30 UTC에 시작했다(약7시간38분 지연). 예약 시각을 정산 제공 시각으로 약속하면 안 된다. 마지막 공개 정산 시각은11/21 16:43:49 UTC다.
- 실제 참여자는0명이며 공개 순위도0명이다. 사용자 성적·보상 지급이나 참여율 개선이 검증된 상태는 아니다.
- 새로 접수 중인 대진은 없다. 11/19 단기 후보는 비활성이며 마감이 지났다. 다음 주 후보 `kr-2026-11-23`도 disabled이고 workflow의 자동 소비 대상이 아니다. 과거 단기 후보를 활성화하거나 기존 원장을 다시 열지 않는다.
- 다음 접수 전 가격 원천/정규장 종가 대조, 거래 일정·기업행사·실제 기준 일봉을 확인해야 한다. 개시 후에는 정상 접수 중 본인 선택 저장·변경을 확인한다. 자동 정산 성공으로 이 검증을 대체하지 않는다. 예약 지연 개선도 별도 운영 과제다.

이번 상태 확인과 홈 크기 조정은 읽기 전용 운영 점검이다. workflow 재실행이나 새 접수 개시·원장 정정은 실행하지 않았다. 이전 대기 상태 설명과 후보 일정은 아래 이력으로 보존한다.

## 적용 범위

기존 Supabase `sector-king` (`jbatgxigzrxwthcmaran`)에 `0018_weekly_match.sql`을 적용했다. 11/9 초기 확인 시 운영 라운드·선택·정산은 0건이었다. 11/16 재확인에서는 `kr-2026-11-16` 게시와 정산 0건을 확인했으며, 개인 선택 데이터는 이번 검사에서 조회하지 않았다. 세 테이블에 RLS가 적용되고 사용자는 본인 선택만 읽는다. 선택 쓰기는 로그인 사용자의 신원을 사용하는 전용 RPC만 허용한다. 운영 원본 가격·감사 JSON은 공개 API에 노출하지 않는다.

자동 정산 보호 마이그레이션 `20261109014835_weekly_match_automatic_guard.sql`도 운영 DB에 적용했다(운영 이력 `20261109015512`). 이 함수는 같은 라운드 잠금 안에서 최신 결과를 다시 확인한다. 이미 확정된 승리·무승부·무효 결과는 자동 작업이 덮어쓰지 못한다. `pending`만 재확인하며 자동 무효는 종료 7일 이후에만 허용한다. 수동 정정은 기존처럼 명시적인 사유와 별도 운영 호출이 필요하다.

## 실행·복구·중지

[Weekly Match workflow](https://github.com/byunginhb/sector-king/actions/workflows/weekly-match.yml)는 `main`에서만 실행한다. 기존 GitHub `CRON_SECRET`, `CRON_TARGET_URL`을 Actions 안에서 재사용하며 값을 복사하거나 출력하지 않는다. 공개 GET과 잘못된 본문 `{}`에 대한 인증 후 HTTP 400 응답으로 서버 연결을 검사한다. 기준일 전에는 `waiting-base`, DB 쓰기 없이 종료한다.

첫 게시 전에 기준 가격과 출처를 `weekly-match-baseline-kr-2026-11-16` artifact에 저장한다. 게시 타임아웃 이후에도 같은 원본을 복원해 재전송한다. 현재 저장소·main·해당 workflow·실행 이벤트·커밋을 확인한 artifact만 복원한다. 이미 게시됐는데 원본이 없거나 설정이 바뀌었으면 중단하며 가격을 다시 만들어 덮어쓰지 않는다.

정산 원본도 전송 전에 별도 artifact로 보존한다. 조회 시간 초과·소켓 오류도 결측 증거로 기록한다. 각 종목의 결측·기업행사는 `pending`으로 남기고 비중을 재분배하지 않는다. 종료 7일이 지나도 미확인이면 무효 처리한다. 확정 결과는 다음 실행에서 건너뛴다. 한 실행은 최대 15분이며 코드 내 즉시 반복 재시도는 없고, 실패 상태와 Actions 요약을 확인한 뒤 원인을 수정한다. 다음 일일 실행은 다시 확인할 수 있다. 추가 이메일·Slack 발송은 설정하지 않았다.

중지: `gh workflow disable weekly-match.yml` 또는 GitHub Actions 화면에서 Disable workflow. 설정의 `enabled:false`도 모든 수집·전송을 중지한다. 이 설정은 웹 진입 노출 플래그와 별개다. 이번 라운드가 확정된 뒤 중지하거나, [다음 후보 전환 조건](weekly-match-next-steps-2026-11-16.md#3-다음-후보-전환-조건)을 모두 확인해 전환한다. `pending`이면 현재 설정을 유지한다. Artifact 보관은 90일이므로 장기 보존이 필요하면 만료 전에 운영 담당자가 내려받아 보관한다. 누락·만료 시 자동 복구는 중단한다.

수동 재실행: `gh workflow run weekly-match.yml --ref main`. 실제 실행 성공, 첫 게시, 첫 접수, 첫 정산을 각각 구분해 확인한다. 새 코드는 새 마이그레이션 적용 후 배포한다. 중지는 원장을 삭제하지 않으며 롤백 시에는 먼저 workflow를 중지하고 기존 데이터를 보존한다.

## 공개 전 남은 검증

11/18 단기 베타는 과거 가격의 정규장 종가 정의 확인이 남아 `enabled:false`다. 메뉴·별도 실행 준비와 실제 접수 개시를 구분한다. 차이와 해결 조건은 [단기 베타 운영 기록](weekly-match-pilot-2026-11-18.md#가격-원천-확인-장애)에 기록했다.

11/16 당시에는 `WEEKLY_MATCH_ENABLED` 기본 false로 섹터 진입을 숨겼다. 11/18 조기 베타 승인 후 이 플래그에 의존하지 않고 전역·섹터 메뉴에서 베타 진입을 제공한다. 검색 `noindex`와 sitemap 제외는 유지한다. 실제 Google 로그인·선택 저장은 사용자가 직접 확인하는 방식으로 남기며, 격리 자동 테스트로 대체 완료 처리하지 않는다.

운영 DB에서는 합성 사용자·라운드를 트랜잭션 안에 만들고 본인 선택 갱신, 타인 기록 차단, 직접 쓰기 거부, 마감 거부를 확인한 뒤 전부 롤백했다. 이 검사는 실제 PostgreSQL/RLS 검사이며 OAuth 로그인 성공을 뜻하지 않는다. 기존 사용자 데이터를 시험에 사용하지 않았다. 공개 anon 키의 실제 PostgREST 조회·쓰기 거부도 확인했다.

기존 Supabase 보안 advisor의 함수 search_path·기존 security-definer 권한·유출 비밀번호 검사 알림은 이번 작업 이전부터 존재한다. 운영 전용 두 테이블의 정책 없는 RLS는 클라이언트 접근을 차단하려는 설계다. 이번 작업에서 기존 인증 설정을 변경하지 않았다.
